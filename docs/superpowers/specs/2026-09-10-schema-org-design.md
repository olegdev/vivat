# Микроразметка schema.org: Organization + BreadcrumbList

Дата: 10.09.2026 · Статус: дизайн согласован, к реализации

Требование пришло от SEO-специалиста клиента, двумя пунктами:

1. Organization — на всех страницах сайта;
2. BreadcrumbList — на всех страницах, кроме главной.

Пример, на который ссылается ТЗ (`4rome.ru`), размечен как JSON-LD и несёт
четыре поля: `url`, `logo`, `name`, `telephone`. Валидатор — `validator.schema.org`.

## Решения

- **Формат — JSON-LD.** Один `<script type="application/ld+json">` на сущность.
  Не трогает ни один класс и ни один пиксель вёрстки, целиком переносится в
  Blade. Микроданные (`itemscope`/`itemprop`) отвергнуты: правки полезли бы в
  каждый партиал и в семь страниц с крошками, а на пятнадцати страницах без
  видимых крошек размечать было бы нечего.
- **Домен — `https://mebel.com`,** записан в разметке буквально. Это живой сайт
  клиента, проект уже знает его в `data/constructor.js`, `data/online-shops.js`
  и `data/contacts.js`.
- **Состав Organization — ровно как в ТЗ:** `name`, `url`, `logo`, `telephone`.
  Ни `address`, ни `email`, ни `sameAs`.
- **BreadcrumbList — на всех страницах, кроме главной,** как просит ТЗ, а не
  только там, где крошки видны (их видно на семи страницах из двадцати двух).
  Видимая вёрстка при этом не меняется нигде.
- **Порождается статически,** руками, в разметке каждой страницы. Не JS: разметка
  — структура, сервер обязан отдавать её сразу (архитектурное правило проекта).
- **Дилерская половина — один адрес на пару.** `dealer/catalog.html` и
  `customer/catalog.html` в бою один URL, разметка меняется по логину. Отсюда
  следствие: у дилерской главной крошек нет — это та же главная.

## Архитектура

**Organization — партиал `src/partials/schema-org.html`,** один на все 22 страницы:

```json
{ "@context": "https://schema.org", "@type": "Organization",
  "name": "VIVAT",
  "url": "https://mebel.com/",
  "logo": "https://mebel.com/assets/header/logo.svg",
  "telephone": "+7 (495) 135-65-65" }
```

Подключается строкой `<!--#include partials/schema-org.html -->` в `<head>`,
сразу после `<title>`. Плагин включений — текстовая склейка, в `<head>` работает
так же, как в `<body>`. В `dist-php/` строка становится
`@include('partials.schema-org')`.

Источники значений: `name` — `alt` логотипа в `partials/header.html`; `telephone`
— номер шапки (`tel:+74951356565`, две позиции); `logo` — `public/assets/header/
logo.svg` (SVG в списке форматов, которые Google принимает).

**BreadcrumbList — свой блок в каждой из 20 страниц.** Партиалом это не
выражается: содержимое у каждой страницы своё, а `<!--#include -->` — плоская
склейка без параметров. В Blade каждый блок станет
`@include('partials.schema-breadcrumbs', ['items' => [...]])`.

## Охват

Разметки крошек не получают: `customer/main.html`, `dealer/main.html` (та же
главная) и `src/index.html` (служебный индекс экранов, не страница сайта).

### Семь страниц с видимыми крошками

JSON повторяет `<nav>` дословно, по одному правилу:

| что | откуда |
|---|---|
| `name` | текст звена в `<nav>`, как есть |
| `item` | `href` того же звена, приведённый к `https://mebel.com/…` |
| последнее звено | без `item` — это текущая страница (схема разрешает) |
| `href="#"` у звена «Каталог» | `/catalog.html` — единственный такой случай, в обоих каталогах |

Цепочки (как они нарисованы в макете):

| страница | цепочка |
|---|---|
| `customer/catalog` | Главная › Каталог › Кухни VIVAT |
| `customer/pdp` | Главная › Каталог › Кухни › Кухня Фьюжн-05 |
| `customer/pdp-module` | Главная › Каталог › Кухни › Флэт › Модули Флэт |
| `customer/action` | Главная › Акции |
| `dealer/catalog` | Главная › Каталог › Кухни VIVAT |
| `dealer/pdp` | Главная › Кухни VIVAT › Кухня Фьюжн-05 |
| `dealer/models` | Главная › 3D модели |

У покупательской PDP «Каталог» и «Кухни» ведут на один адрес — так нарисовано;
правило «разметка отражает видимое» важнее косметики, а в Blade звенья получат
разные параметры каталога (шов из решения №7 в `LINK-MAP.md`). Дилерские каталог
и PDP несут **свои** крошки, а не покупательские: у дилерской PDP их три.

### Тринадцать страниц без крошек

Двухзвенная цепочка «Главная › имя страницы». Имя не выдумано: у `order`,
`constructor` и `contacts` это их `<h1>`; у восьми страниц раздела «Для бизнеса»
— их `<h2>` (H1 там — название раздела, имя страницы стоит первой строкой правой
колонки).

`customer/order` и `dealer/order` — «Мой заказ» · `dealer/constructor` —
«Конструктор мебели» · `dealer/contacts` — «Контакты» · `delivery` — «Доставка» ·
`online-shops` — «Для интернет-магазинов» · `howto` — «Как с нами работать?» ·
`certificates` — «Сертификаты» · `schemes` — «Схемы сборки» · `tech-info` —
«Техническая информация» · `decors` — «Каталог декоров» · `news` — «Новости» ·
`learning` — «Обучающие материалы».

**Промежуточного звена «Для бизнеса» нет.** У раздела нет своей страницы: по
решению №3 ссылка ведёт на `howto.html` — соседнюю страницу, а не хаб. Звено без
адреса Google пометит предупреждением, звено на `howto` соврёт о структуре.

## Порядок работ

2. Строка включения в `<head>` всех 22 страниц.

4. Абзац в `docs/PORTING.md`: домен заменяется на `url()`, адреса звеньев — на
   `route()`, партиал — обычный `@include`.
5. Записи в `BACKLOG.md` (ниже).

## Проверка

**`scripts/check-schema.mjs`, команда `npm run schema`.** Проход по собранному
`dist/pages/**/*.html`; на каждой странице утверждается:

- JSON парсится;
- Organization ровно один и несёт все четыре поля;
- BreadcrumbList есть везде, кроме двух главных;
- `position` идут 1…n без пропусков;
- у всех звеньев, кроме последнего, есть абсолютный `item`;
- **тексты звеньев совпадают с видимым `<nav>`** там, где `<nav>` есть.

Последняя проверка — та, ради которой скрипт и пишется: двадцать блоков JSON
набиты руками, и расхождение крошек с разметкой после правки текста — самая
вероятная поломка. Остальное проверяется заодно, потому что проход уже сделан.

**Живая сверка:** `validator.schema.org` принимает вставленный фрагмент —
прогнать по одной странице каждого типа (главная, каталог, PDP, страница
раздела).
